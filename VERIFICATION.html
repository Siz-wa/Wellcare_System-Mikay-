WellCare — Verification Steps

Phases 1–3, plus the Phase 0 checks they depend on. Work top to bottom; later steps assume earlier ones passed.

That now also runs the task scheduler (added in 0.2), so anything time-based works while it is up. Leave it running. Use the second terminal for the php artisan commands below.

Phase 0 — Correctness

Short checks. Everything later depends on these.

0.1 — The clinic day sorts correctly

The bug: times were stored as display strings ("9:00 AM") and sorted alphabetically, so the afternoon came first on five screens.

C:\xampp\mysql\bin\mysql.exe -u root wellcare_db -e "SELECT appointment_time, TIME(appointment_at) AS real_time FROM appointments ORDER BY appointment_at LIMIT 10;"
the times run in real chronological order (8:00 AM, 8:30 AM, 9:00 AM …). Compare with ORDER BY appointment_time in the same query — that still returns 1:00 PM first, which is what every screen used to show.

Then log in as a doctor and open Appointments. The list must run earliest-first across the day.

0.2 — The scheduler is alive

php artisan wellcare:scheduler:status
it reports "Scheduler is alive" while composer dev is running. Stop composer dev, wait 30 minutes (or run php artisan wellcare:scheduler:status --stale-minutes=0), and it must report failure instead. Check the exit code with echo $? — 0 when alive, 1 when stale. That exit code is the contract a monitor uses.

0.3 — Retention is per record type

php artisan wellcare:records:purge
it prints a table of four record classes with different periods, each with its source, and a warning that the figures are UNVERIFIED. It must delete nothing.
Action for you: those numbers came from secondary reporting of DOH issuances — the primary PDFs would not parse. They must be confirmed by whoever acts as your DPO before RETENTION_PURGE_ENABLED is ever set true.

0.4 — Staff must use two-factor

  1. Log in as dr.reyes@wellcare.com.
  2. You are sent to Settings → Security, via a password confirmation step.
  3. Try to navigate to /doctor/appointments directly — you are sent back.
  4. Enrol with an authenticator app, then retry.
an un-enrolled doctor cannot reach any clinical page, and reaches all of them after enrolling. Also confirm a patient account is never asked — 2FA is deliberately optional for patients.

Phase 1 — Safety gates

1.1 — Prescribing, and the allergy check

Before this task, doctors could not prescribe at all — the UI existed but was never wired to anything.

First give a patient an allergy. As a doctor, open Patient Records, pick a patient, and add an allergy: allergen Penicillin, severity severe, reaction Anaphylaxis.

Then try to prescribe against it.

  1. Open Consultations and start/open a session for that same patient.
  2. Go to the new Prescription tab. The patient's allergies are listed at the top.
  3. Add a medication named Amoxicillin 500mg and save.
the save is refused. A red panel names the allergen, its severity and the recorded reaction, and says it is a "Same drug family" match — Amoxicillin is a penicillin.

Now confirm the refusal was total: change the SOAP notes before saving, get refused, then reload. The SOAP text must not have saved either — the whole save rolls back together, so you never end up with a note plus silently dropped medications.

Then override it. Type a reason of at least 10 characters and save again.

the prescription saves, and the override is recorded:
C:\xampp\mysql\bin\mysql.exe -u root wellcare_db -e "SELECT description, causer_id, properties FROM activity_log WHERE description LIKE '%Allergy warning overridden%' ORDER BY id DESC LIMIT 3;"
a row exists — and the properties column contains neither the drug name nor the allergen. That is deliberate: a drug name discloses the diagnosis by inference, and activity_log is readable by admins. The clinical detail goes to storage/logs/laravel.log instead.

Check it does not over-fire. Prescribe Paracetamol 500mg to the same penicillin-allergic patient — it must save with no warning at all. A checker that cries wolf is worse than none.

Known limit, state this in your defence: this is name matching over a hand-written ingredient table, not a drug database. It will miss brands it does not know, misspellings and compound preparations. A silent result means "nothing matched the table", never "this drug is safe."

1.2 — Notifications leave the application

Previously every notification was database-only: visible solely to someone already logged in, looking at the bell.

  1. As a doctor, confirm any pending appointment.
  2. Open storage/logs/laravel.log.
you see the confirmation email rendered in the log (the mail driver is log), and an SMS (not sent — log driver) entry showing the message and the normalised +63… number.

Check channel independence. As the patient, go to Settings → Notifications and switch off in-app appointment notifications. Have the doctor cancel that appointment.

no bell notification appears for the patient, but the email and SMS entries still appear in the log. Turning off the bell must not silence the other two — they are separate channels on the settings screen and must behave that way.
Not yet real delivery. SMS_DRIVER=log writes messages to the log rather than sending them — the whole path is real, only the last hop is simulated. Email becomes genuinely live the moment MAIL_MAILER is pointed at real SMTP; that costs nothing. SMS needs the clinic to choose and pay for a provider.

1.3 — Critical results cannot be ignored

  1. As a doctor, order a lab test from within a consultation.
  2. Log in as a nurse and record that result with severity critical.
  3. Back as the requesting doctor, open the bell.
the critical result appears with an Acknowledge action, distinct from simply reading it.

Confirm reading is not acknowledging. Mark it read, then:

C:\xampp\mysql\bin\mysql.exe -u root wellcare_db -e "SELECT id, type, `read`, read_at, acknowledged_at, escalation_count FROM appointment_notifications WHERE type='lab_critical' ORDER BY id DESC LIMIT 5;"
read_at is set but acknowledged_at is still NULL. Opening a notification is not the same act as accepting a critical value, and the audit trail must not claim it is.

Now test escalation. Age the alert past the 15-minute threshold and run the sweep:

C:\xampp\mysql\bin\mysql.exe -u root wellcare_db -e "UPDATE appointment_notifications SET created_at = DATE_SUB(NOW(), INTERVAL 2 HOUR) WHERE type='lab_critical' AND acknowledged_at IS NULL;"
php artisan wellcare:results:escalate --dry-run
php artisan wellcare:results:escalate
the dry run lists the waiting result and changes nothing; the real run escalates it, escalation_count becomes 1, and the log shows the alert going to nurses and admins — not back to the doctor who already did not respond. Run it three more times: it stops at 3 escalations rather than nagging forever.

Finally, click Acknowledge and re-run the sweep — it must report nothing to escalate.

Phase 2 — Operational

2.1 — Appointment reminders

The reminder notification type had existed since the table was first created and was sent by nothing.

php artisan wellcare:reminders:send --dry-run

If nothing is listed, create something in the window — book an appointment about two days out and confirm it as the doctor. Then:

php artisan wellcare:reminders:send
the appointment is reminded, and storage/logs/laravel.log shows the reminder email and SMS.

The most important check — it must not re-send. Run the same command twice more.

it reports nothing due. Verify directly:
C:\xampp\mysql\bin\mysql.exe -u root wellcare_db -e "SELECT id, appointment_date, appointment_time, reminded_ahead_at, reminded_same_day_at FROM appointments WHERE reminded_ahead_at IS NOT NULL LIMIT 5;"
the timestamp is stamped once and does not move. A reminder system that re-sends is worse than none — it is the fastest way to teach a patient to ignore the clinic.

The subtle case: as the patient, turn off in-app appointment notifications, then book and confirm another appointment two days out and run the sweep. No bell notification appears — but reminded_ahead_at must still be stamped, and a second sweep must still send nothing. (If this were derived from the notification rows instead, that patient would be re-reminded every 15 minutes forever.)

2.2 — Reschedule

Previously the only path was cancel-then-rebook, which releases your old slot before securing the new one.

  1. As a patient, note an existing confirmed appointment's date, time and ID.
  2. POST a reschedule to /appointments/{id}/reschedule with appointment_date and appointment_time. (There is no UI button yet — see the note below.)
the appointment moves and keeps its ID:
C:\xampp\mysql\bin\mysql.exe -u root wellcare_db -e "SELECT id, appointment_date, appointment_time, appointment_at, status FROM appointments WHERE id = YOUR_ID;"
same id, new date/time, and appointment_at updated to match. A cancel-and-rebook would have produced a new row and lost the history.

Then confirm the old slot is free again — open the booking page for that doctor and date; the original time must be offered.

Backend only. The route, transaction and all guards are built and tested, but there is no reschedule button in the patient UI yet. Verify with a REST client or curl (you will need a session cookie and CSRF token), or trust the 19 automated tests in tests/Feature/Booking/RescheduleTest.php. Adding the button is a small front-end task if you want it for the defence.

Phase 3 — Clinical depth

3.1 — Vitals are measurements, not text

All six vitals were stored as display strings with units baked in, which made trends, BMI and range checks impossible.

Check the historical data was converted:

C:\xampp\mysql\bin\mysql.exe -u root wellcare_db -e "SELECT blood_pressure, systolic, diastolic, heart_rate, heart_rate_bpm, temperature, temperature_c FROM consultation_sessions WHERE systolic IS NOT NULL LIMIT 5;"
every string has a matching number beside it — 119/83 became 119 and 83, 70 bpm became 70.

Check it did not invent any readings — this is the one that matters most:

C:\xampp\mysql\bin\mysql.exe -u root wellcare_db -e "SELECT MIN(heart_rate_bpm) min_hr, MIN(systolic) min_sys, MIN(temperature_c) min_temp FROM consultation_sessions;"
no zeros. MySQL casts unparseable text to 0, so a careless backfill records a heart rate of zero — clinically impossible, and unlike a NULL it looks like a real measurement somebody took.

Then record new vitals through a consultation and re-query that session: both the display strings and the numeric columns must be written.

Backend only, same as 2.2. The trend query (ConsultationSession::vitalsTrendFor()), BMI and out-of-range flagging are built and tested, but not yet drawn on a chart in the UI. The chart is the visible payoff and is a front-end task — worth doing before the defence, since a BP trend line is the most convincing screen in the system.
Deliberate limitation: range flagging uses adult reference ranges and returns nothing for patients under 18. A healthy toddler's heart rate of 130 is far outside every adult range, and flagging it would train clinicians to ignore the flag. An empty result therefore means "nothing to flag or not assessable" — never "everything is normal."
